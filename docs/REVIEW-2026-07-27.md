## 二、做得好的地方

这些在同类早期项目里少见，不是客套：

1. **分层不是口头约定而是机械门禁** — `src/runtime/architecture-guard.test.ts:66-101` 遍历所有 import specifier，禁止 runtime/extensions 反向依赖 tui，并断言未上线组件不出现在默认装配路径。实测 runtime→tui 引用数为 0。

2. **「失败可观测」红线有正面样本** — `src/runtime/context-compaction.ts:273-293` 在工具批次不完整时抛错拒绝压缩；模型返回空摘要 / 返回 tool_calls / 压缩后没变小，三种情况全部抛错而非假装成功。全仓 `} catch {}` 静默捕获仅 31 处（0.15%/行）。

3. **WAL 设计粒度确实比竞品细** — 工具批的意图记录在工具执行**之前**就 fsync 落盘（`session-wal.ts:214-227`；`agent-loop.ts:526-533`），resume 因此能准确知道哪几个工具处于未知完成态；恢复时不重放被打断的工具，而是合成 `role=tool` 错误结果保住 provider 侧配对（`session-recovery.ts:43-60`），避免「恢复即重复执行副作用」。

4. **TurnSnapshot 是有真收益的抽象** — `harness/turn-snapshot.ts:50-67` 每次请求前把 model/client/tools 冻结成不可变视图，使 `/model` 热切换与扩展动态注册工具不污染 in-flight 请求。

5. **零遥测是代码事实不是文案** — 全仓仅 1 处非 provider 出网（`update-check.ts:182`，npm 查版本），只发 `UA=xiocode-update-check/<version>`，无任何标识，可关；README:235 主动点名了这唯一一个请求。

6. **凭证卫生到位** — 目录 0700 / 文件 0600 且写后再 chmod（`credentials.ts:50,64-65`）；config.toml 明确「never write API keys」；provider 报错与 doctor 输出都不回显 key。

7. **成本从不撒谎** — `pricing.ts:82-88,97-103,148-151`：未定价显示 `~unknown` 而非 `$0`，极小值显示 `<$0.0001`，混入未定价响应时总额加 `+` 表示下限。

8. **恶意仓库无法改写信任根** — 配置只从 HOME 读（`ensure-config.ts:15-17`），仓库里放什么 config 都无效；`[extensions]` 只是内置扩展开关，没有「任意模块路径」插件加载面。

9. **中英双 README 同步度极高** — 两份都恰好 225 行、10 个二级标题一一对应，逐行 diff 唯一差异是被翻译的示例串。文档命令集与代码 100% 对齐，**无幽灵命令**。

10. **0 用户没被任何文档掩饰**，且度量口径在用户到来之前就写死（二值主指标 + 8 类失败归因 + 三条决断线，含「获取不到 10 个用户即终止命题」）。

11. **DeepSeek 适配确实超过「配个 base_url」** — 流式 `reasoning_content` 解析成 thinking_delta（`providers/client.ts:577-581`）、按官方档位映射 reasoning_effort、缓存命中独立计价。**深度是真的，问题在宽度。**

12. **发布面干净** — `npm pack` 仅 64 文件 / 287KB，无 src、无 map、无凭证；`prepack` 串起 typecheck → build → prepack-check 三道闸。技术债标记密度极低：47k 行生产代码里 TODO/FIXME/HACK 仅 3 处。

## 三、A 类 · 会让用户丢东西

### A1 · WAL 撕裂尾记录 = 全部会话打不开，且产品内零修复入口

**critical · CONFIRMED（两个独立代理各自复现）**

- 证据：`src/runtime/session-wal.ts:249-274`、`session-store.ts:246-252,427,460-462`、`cli/session-resume.ts:41-48`
- `readJournal` 对任何无法解析的行直接 throw，**包括「崩溃时写了一半的最后一行」**——而这恰恰是 append-only 日志存在的全部理由。
- `SessionStore.list()` 没有 per-session 隔离：**一个坏会话会让 `xio --continue`、`xio resume --list`、会话选择器对所有会话失效**。
- `xio resume --delete` 也走 `store.load()`（`run-agent-cli.ts:219`），被同一个 throw 堵死——**唯一疑似出口也没了**。
- 更易触发的同源问题：`#loadVersioned` 在 state.json 缺失时回落读 metadata.json，ENOENT 直接抛出。**一个空的会话目录**（新会话首次落盘期间被 kill 就会留下）即可让 `list()` 对全部会话永久 ENOENT。
- 现有测试把这个行为**固化成了期望**（`session-wal.test.ts:144-161`、`session-store.test.ts` 用例名即 "fails closed on corrupt journal"）。

**修法**：`readJournal` 区分「中间行损坏」（继续 fail-closed）与「末行不完整」（截断 + 可见 warn）；`list()` 逐会话 try/catch，坏会话标记 degraded 而非让整表抛错；`doctor` 增加会话目录体检 + 提供修复命令。

### A2 · snapshot 与 truncate 之间崩溃 → 消息重复且永久固化

**critical · CONFIRMED**

- 证据：`session-store.ts:317-318,99-103`、`session-wal.ts:300-302,322-331`
- 顺序是 `writeJsonAtomicDurable(state.json)` → `truncateJournal()`，两步之间没有任何水位标记（`stateV2Schema` 只有 revision，与 journal seq 无关），`applyJournal` 的 append 分支是无条件 `push`。
- 实测：3 条消息的会话恢复出 5 条，`tool_call id` 重复两次 → provider 直接 400，**恢复出来即刻不可用**；且 resume 后 `history.persist()` 会把重复历史写成新基线，污染永久固化。
- 核验代理补充：暴露窗口是 rename 到 truncate 之间的几毫秒，单次崩溃命中概率低于原判断——但一旦命中无自救路径。

**修法**：state.json 持久化 `applied_seq`，只回放 `seq > applied_seq`；或改为「写 state.tmp → truncate journal → rename」，让 rename 成为唯一提交点。

### A3 · FileWriteQueue 不保证 FIFO

**medium · 核验代理实测发现（原审计漏掉）**

- 证据：`src/runtime/file-write-queue.ts:15-20`；`streaming-tool-scheduler.ts:118`
- `run()` 在入队前 `await realpath`（走 libuv 线程池），谁先拿到结果谁先入队，与调用顺序无关。注释只保证互斥，不保证顺序。
- 实测同路径双写 **300 轮反转 49 次 ≈ 16%**。含义：模型在一个 turn 里对同一文件先 write 再 edit，约 1/6 概率被反序执行。
- `streaming-tool-scheduler.test.ts:143` 的偶发失败是**真阳性**，不是噪声。

### A4 · 并行工具批被 kill 会丢掉已完成工具的全部输出

**high · CONFIRMED** — `agent-loop.ts:1091`：`recordTurnToolResult` 与 `tool.result` 事件都在 `Promise.all` 之后的同一循环里，连事件总线与 trajectory 都拿不到已完成工具的结果，无任何旁路补救。恢复时 6 个工具全被标成 completion unknown。

### A5 · 用户源文件写入非原子

**medium · CONFIRMED（严重度经核验下调）** — `tools/builtin.ts:147-149,237-241` 是 truncate-then-write，同仓明明有 `writeJsonAtomicDurable` 可用。核验反证：默认 `require_read_before_edit=true` 使原文通常已进 journal 或 spill 文件，**缺的是恢复 UX 不是数据**。

## 四、B 类 · 让新用户第一分钟就失败

### B1 · 用户现在装到的不是你写的东西

**critical · CONFIRMED（性价比最高的一条）**

npm latest = 1.1.1，发布于 07-22；Route B Phase 1 四个模块（doctor / feedback / pricing / command-risk）在 07-26 的 `2ec781d` 才首次落地。**任何渠道装到的版本：没有 doctor、没有成本显示、没有危险命令拦截、没有 feedback。** README 的 pin 示例还写着 1.1.1。

### B2 · README 首屏的 `xio "add a login page"` 在任何第一次使用的目录里都改不了文件

**high · CONFIRMED**

- 证据：`config-parser.ts:403-405`（`DEFAULT_TRUST = { mode: "ask" }`）、`session.ts:215-226`、`project-trust.ts:341-347`、`tool-permission.ts`
- `interactiveSession = options.promptOnce === undefined`，所以带 prompt 的一次性调用一律是非交互 → 未知路径 → untrusted → write/exec 解析为 `deny`。
- `project-trust.test.ts:365-393` 把该行为固化为期望，**这是有意设计而非疏漏**，修复要动测试。
- 用户看到的唯一线索是一行机器味的 `[status:trust] trust:untrusted`，文案完全不提 write/exec 被拒。
- 同源：`xio -p` 在未授信仓库里**静默跳过全部项目上下文**（CLAUDE.md / skills / hooks / MCP），与 README:184 的宣传直接冲突，而 CI/脚本场景恰恰只用 `-p`，且首次运行必然命中（无非交互授信入口）。

### B3 · 非 TTY 下裸 `xio` 挂死

**high · CONFIRMED** — exit 13 + Node 内部 unsettled-TLA 警告，无任何可执行信息。trust ask 链路上没有任何 TTY 守卫。**在完全没配 key 时也会走到，CI/docker 冒烟必撞。**

### B4 · `xio doctor` 完全无视 config.toml 里的 providers

**high · CONFIRMED** — doctor 全文没有任何读取 `runtimeConfig.providers` 的分支，connect 探测只 `for PROVIDER_PRESETS`。双向误判：**自定义网关（正是国产模型主要接入方式）会得到假 FAIL**。

### B5 · 首启输出的四个问题

**medium · CONFIRMED（实测）**

- **中文泄漏到英文产品首屏**：`grep 顺序: ugrep → rg`、`grep 首选（内容搜索）`、`优于 find`
- **同一个「没配 key」用三种措辞讲三遍、6 个箭头**
- **`[info] hint: capture private regression — /regress`** — 被 Phase 0 判定「移出默认叙事」的实验面，在新用户第一次失败时主动推销自己；且该 kill-switch 在 `-p` 模式下**根本不生效**（`/regress` 无条件注册，`offer_on_failure` 只覆盖交互路径）
- 内部状态标记 `[status:trust]` / `[status:permission]` / `[status:workspace]` 直排 stdout，污染 `-p` 的可脚本化输出

### B6 · 价格表与国产模型

**high · CONFIRMED** — `PRICE_TABLE_VERSION` 定死后从未被使用；substring 匹配会把网关模型算成直连价；除 DeepSeek 外**零国产 provider preset**（Kimi / GLM / Qwen / moonshot / dashscope 全仓命中数 = 0）；catalog 与价格表停在 V3 代，而仓库自己的测试里用了 64 次 v4 id → **主打 provider 的旗舰模型成本显示为 `~unknown`**，直接打脸计划书 §1「显示真实美元成本，不是 null」。

## 六、D 类 · 可信度与工程门

### D1 · 跑一次测试就污染真实安全库

**high · CONFIRMED（活体复现）** — `prepareSession` 未传 projectTrust 时 `ensureProjectTrust` 回落 `os.homedir()`。实测开发者真实 `~/.xiocode/trust.json` 有 **53 条 entry，全部是测试临时目录、全部 `trusted`，没有一条真实项目**；核验代理跑完测试后涨到 56。污染面还包括 `~/.xiocode/runs` 与 `~/.xiocode/perf`。

### D2 · `npm test` 随机红

**high · CONFIRMED** — 仓库无任何 vitest 配置 → 默认 5s 超时 + 无并发上限 + 大量真实子进程/真实 sleep 测试。三次全量跑失败集合两两不同，单独跑全绿。CI 在 2 核 runner 上只会更糟。**准确表述是「高频随机红」而非「恒红」。**

### D3 · CI 从不验证会发出去的东西

**medium · CONFIRMED** — build 之后没有任何一步碰过产物，`dist/xio.js` 从未被自动执行过一次；无 npm pack、无 lint（仓库无任何 linter 配置）、无 coverage、单 OS 单 Node、**无 release workflow**（publish 是本地手工，prepack 链缺 test）。

### D4 · P95 门控只关掉两处中的一处

### D7 · 规模与依赖

- **一个只用 4 个 client class 的依赖拖来 92 包 / 10.3MB**，并把全部 3 个生产漏洞（含 1 个 high）带给用户；CI 无 `npm audit`、无依赖机器人，精确锁死只会让它烂在原地
- **跨扩展耦合让「冻结」的 eval 代码删不掉**：一个 3 行 sha256 helper 把 eval 的 suite-loader + 硬编码 fixtures 拖进默认会话静态图
- **发布了未文档化的第二个全局命令 `xio-improve`**，默认目标是修改 xiocode 自己仓库的 `docs/self-improve.md`；无 key 时抛裸 Error 栈
- **`--xio-fast` 帮助文本说反了**：实际关掉的是 MCP + hooks + skills + AGENTS.md 读取，而这些是 README 明写的产品能力
- **464 行 Trellis 并行派发只有作者本机能用**（依赖仓库外的 `.trellis/scripts/task.py`），却把 Trellis 概念写进每个用户的 system prompt 和工具 schema
- **microcompact 在没有 spill 时被整段丢弃**（`tool-result-budget.ts:167-175`）：`keep_tool_rounds` 的旧轮次截断完全不生效，结果被算出来然后扔掉。直接打在「长会话不卡顿」上
- **`~/.xiocode/runtime-config.json` 跨进程共享且非原子写**：第二个 xio 启动会污染第一个进程的配置，窗口无界（取决于用户何时回答 trust 提问）
- **同一目录两个 xio 进程之间没有任何互斥**；lease 存活判定把「pid 存在」当作活着，pid 复用会永久挡住 resume 且无 `--force`

## 七、定位判断

**三个钩子在 2026 年中的真实处境：**

| 钩子 | 判断 |
|------|------|
| 长会话韧性 | 技术底子是全项目唯一「别人没做到这个粒度」的资产，但用户可感知的那半（`/rollback`）绑死在默认关闭的 worktree 上，且 A1/A2 让它在真崩溃场景下反而成为单点故障 |
| 零遥测 BYOK | 站得住，但已商品化——属于「别人也有只是没宣传」那类 |
| 合入权在人 | merge gate 是 UX 关口不是强制边界。GOAL.md 自己诚实声明了，但 README tagline 把它说成硬保证 |

**「国产模型一等公民」的赌注**：宽度为 1（只有 DeepSeek），深度停在 V3 代。且缝隙**已被占位**——专注 deepseek-v4 的 Deep Code 已有约 1990 star 且 07-25 仍在推。差异化窗口以月计，不以年计。

**最诚实的判断**：这是一个工程质量高于平均线的**自用工具 + 作品集**，套着一层写得很认真的产品化计划书。25.5% 的代码是自认冻结的实验面，两张度量表是空的，计划书自己写着「盲测未做，需要真人」。

**瓶颈不在代码，在分发。** GitHub 仓库公开 11 天，description 空、topics 空、0 release、0 issue。计划书 Phase 2 写着「GitHub topics + awesome-list PR」——那两个字段填一下是 30 秒的事，11 天没做。这比任何一个 bug 都更能解释 0 用户。
