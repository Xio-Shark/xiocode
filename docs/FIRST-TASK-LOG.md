# 首任务成功率日志（内部度量，不进对外叙事）

> 依据 [ROUTE-B-PRODUCT-PLAN.md](./ROUTE-B-PRODUCT-PLAN.md) §3.5。
> **韧性钩子把用户带进门，第二周还在不在取决于 agent 能不能把任务做对。**
> 对外砍掉 eval 叙事 ≠ 内部放弃度量。没有这张表，Phase 3 决断时只知道
> 「留存了没有」，不知道「为什么」，退出访谈会变成瞎猜。

## 记的是什么

**每一个**盲测者、每一个 Phase 2 真实用户，都记同一个二值指标：

| 字段 | 说明 |
|------|------|
| 日期 | ISO 日期 |
| 来源 | `blind`（盲测朋友）/ `linux.do` / `v2ex` / `HN` / `reddit` / `其他` |
| 环境 | OS + Node 版本 + 安装渠道（install.sh / npm） |
| Provider/模型 | 他实际用的，不是我推荐的 |
| 安装是否一次成功 | ✅ / ❌ + 卡在哪一步 |
| **首任务成功** | ✅ / ❌ — 唯一的二值主指标 |
| **失败原因** | 见下方分类；❌ 时必填，不许写「不清楚」 |
| 第二周仍在用 | ✅ / ❌ / 未到期 |
| 原话 | 抱怨用他自己的话记，别翻译成需求 |

## 失败原因分类（先归类，再修）

归类决定修哪一层，别混：

- `install` — 装不上（Node 版本、权限、网络、平台）
- `onboarding` — 装上了但不知道下一步（没密钥、不知道输什么）
- `config` — provider/模型配错、连不通、429
- `agent-wrong` — agent 跑了但把任务做错了（**模型 + 提示词 + 工具质量**，这条最贵）
- `agent-slow` — 做对了但慢到放弃
- `tui` — 界面卡顿/闪烁/滚动/按键
- `trust` — 做对了但用户不敢用（怕它乱改、怕上传代码）
- `env` — 用户环境特有问题（WSL、代理、奇怪 shell）

> **`agent-wrong` 是需要单独盯的一类。** 其余各类都能靠工程修；这一类要靠
> 内部 `xio eval` 做任务质量回归（对外冷冻，内部保留最小用法），不必重造度量工具。

## 决断线（照抄计划 §5，防止事到临头改口径）

- ≥ 4 个用户两周留存 → 产品命题成立，规划下一个 90 天
- 有用户但零留存 → 钩子错了，用退出访谈换钩子再试一轮
- 连 10 个试用用户都获取不到 → 命题终止，回作品集收尾

## 纪律

- 盲测**当场**记，别事后回忆；回忆会把失败记成「他不太会用」
- 一条抱怨对应一条记录，不合并、不美化
- 首任务成功的定义：**用户认为任务完成了**，不是 agent 自称完成
- 这张表不进 README、不进对外叙事；它只用来决定修什么
